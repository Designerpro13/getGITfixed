# Spec generation and issue-fetch pipeline

`spec-gen.ts` fetches a GitHub issue via Octokit, generates three Markdown spec files
(`requirements.md`, `design.md`, `tasks.md`), and writes them under `.kiro/specs/issue-fix/`.
`tsc --noEmit` is clean and all 36 tests pass, but ESLint exits 1 with 45 errors — 28 of them
in this file, all from `number` values interpolated raw into template literals. Beyond the lint
pile there are three convention violations and an `isMain` guard that silently breaks under the
compiled output.

**Watch for:**
- **confirmed** — `@typescript-eslint/restrict-template-expressions` fires on every `issue.number` interpolation (28 sites across `spec-gen.ts` alone); the fix is one `String(issue.number)` call or a local `const num = String(issue.number)` at the top of each generator.
- **confirmed** — `isMain` detection in `spec-gen.ts` (and `pipeline.ts`) is fragile: the comparison works in `tsx` execution but silently breaks under `node dist/spec-gen.js` because `.replace(/\.js$/, ".ts")` is applied to the *running* path, not to `import.meta.url`.
- **confirmed** — `writeSpec` does not wrap `writeFile` or `mkdir` in try/catch, so filesystem errors surface as undecorated OS errors with no context — violating the project's own error-wrapping convention.
- **confirmed** — `fetchIssue` creates a fresh `Octokit` instance on every call, re-reading `GITHUB_TOKEN` each time; a minor inefficiency with a larger convention implication (the token is re-read rather than injected, making the function harder to test without environment mutation).

**Verdict**: NEEDS_CHANGES

---

## High-level view

`writeSpec` does three parallel `writeFile` calls under a single `mkdir`. Neither call is wrapped,
so any I/O failure propagates as a raw `ENOENT` or `EACCES` with no context — violating the
project's own error-wrapping convention. The caller `generateSpec` would surface an opaque OS
error with no indication of which file or path was involved.

`fetchIssue` constructs a new `Octokit` on every invocation and reads `GITHUB_TOKEN` each time.
The test suite works around this by mutating `process.env` in `beforeEach`, which leaks env state
between tests. An optional `octokit` injection parameter would eliminate that.

The `isMain` guard uses a `.replace(/\.js$/, ".ts")` heuristic that works under `tsx` but fails
for the compiled `dist/` output, where both `process.argv[1]` and `import.meta.url` end in `.js`
— the replace converts `argv[1]` to `.ts` but `import.meta.url` stays `.js`, so the comparison
evaluates `false` and the CLI entry point never fires when run as `node dist/spec-gen.js`.

The dominant lint signal is the 28 `restrict-template-expressions` errors across the generator
functions — all from `${issue.number}` where `issue.number` is typed as `number`, which
`strictTypeChecked` forbids without an explicit conversion. This is the only thing keeping `npm
run lint` from passing.

<details>
<summary>Issues (6)</summary>

1. **Template literal number interpolation — 28 lint errors** — `issue.number` (a `number`) is interpolated directly in template literals throughout all three generator functions and the CLI guard. `strictTypeChecked` forbids this. Add `const issueNum = String(issue.number)` at the top of each generator and replace all `${issue.number}` with `${issueNum}`. Same fix needed in `pipeline.ts` (9 additional sites).

2. **`isMain` guard breaks in compiled output** — `fileURLToPath(import.meta.url).endsWith(process.argv[1].replace(/\.js$/, ".ts"))` strips `.js` from `argv[1]` and compares to a path that ends in `.ts`, which works under `tsx` but fails under `node dist/spec-gen.js` where both paths end in `.js` and the comparison evaluates `false`. Replace with `import.meta.url === pathToFileURL(process.argv[1]).href` or compare after normalising both to the same extension. The same bug is present in `pipeline.ts`.

3. **`writeSpec` swallows I/O errors without context** — neither `mkdir` nor `writeFile` is wrapped in try/catch, violating the project convention ("Wrap external I/O in try/catch and rethrow with context"). An `EACCES` on the spec directory would surface as an undecorated OS error with no indication of which file failed. Wrap each write (or the whole `Promise.all`) and rethrow with `Failed to write spec file at ${path}`.

4. **`GitHubIssue.labels` typed as `Array<{ name: string | undefined }>` — ESLint array-type error** — Should be `Array<T>` → `T[]` per `@typescript-eslint/array-type`. Minor, but it's one of the 45 lint errors blocking a clean `npm run lint`.

5. **`fetchIssue` creates a new `Octokit` per call** — the token is re-read from `process.env` and a new client is instantiated every invocation. The convention calls for a centralised `getEnv` (present), but the client construction pattern makes the function impossible to call without a side-effectful environment. Consider accepting an optional `octokit?: Octokit` parameter (used in tests via injection, defaulting to a freshly constructed instance in production) to avoid test-environment mutation.

6. **`verify-mcp.ts` `isMain` uses `includes("verify-mcp")` heuristic** — `process.argv[1]?.includes("verify-mcp")` is fragile if the path contains `verify-mcp` in a parent directory name. Not part of `spec-gen.ts` itself, but the same `isMain` pattern is copied from there; fixing `spec-gen.ts` should drive a consistent fix here too.

</details>

### `isMain` guard fails in compiled output

```typescript
const isMain =
  process.argv[1] !== undefined &&
  fileURLToPath(import.meta.url).endsWith(process.argv[1].replace(/\.js$/, ".ts"));
```

Under `tsx src/spec-gen.ts`:
- `import.meta.url` → `.../src/spec-gen.ts`
- `process.argv[1]` → `.../src/spec-gen.ts`
- `.replace(/\.js$/, ".ts")` → no-op (already `.ts`)
- comparison: `spec-gen.ts`.endsWith(`spec-gen.ts`) → `true` ✓

Under `node dist/spec-gen.js`:
- `import.meta.url` → `.../dist/spec-gen.js`
- `process.argv[1]` → `.../dist/spec-gen.js`
- `.replace(/\.js$/, ".ts")` → `.../dist/spec-gen.ts`
- comparison: `spec-gen.js`.endsWith(`spec-gen.ts`) → `false` ✗

The entry point never fires when the compiled binary is called directly. The robust replacement is:

```typescript
import { pathToFileURL } from "node:url";
const isMain = import.meta.url === pathToFileURL(process.argv[1] ?? "").href;
```

### `writeSpec` missing error context

The project convention (from `code-conventions` steering) mandates:

```typescript
try {
  await writeFile(path, content);
} catch (err) {
  throw new Error(`Failed to write spec file at ${path}: ${String(err)}`);
}
```

`writeSpec` currently does:

```typescript
await Promise.all([
  writeFile(paths.requirements, files.requirements, "utf-8"),
  writeFile(paths.design, files.design, "utf-8"),
  writeFile(paths.tasks, files.tasks, "utf-8"),
]);
```

A permission error on any of the three paths produces `Error: EACCES: permission denied, open
'/…/requirements.md'` with no indication which write failed or why the bot is trying to write
there. The same applies to `mkdir`. Wrap the whole block:

```typescript
try {
  await mkdir(SPEC_DIR, { recursive: true });
  await Promise.all([...]);
} catch (err) {
  throw new Error(`Failed to write spec files to ${SPEC_DIR}: ${String(err)}`);
}
```

### `fetchIssue` couples token read to invocation

Every caller must have `GITHUB_TOKEN` set in the environment, and the test suite works around
this by mutating `process.env` in `beforeEach` — leaked env state between tests. An optional
`octokit` parameter eliminates the mutation:

```typescript
export async function fetchIssue(
  issueNumber: number,
  owner = "Designerpro13",
  repo = "hb-frontend",
  octokit?: Octokit,
): Promise<GitHubIssue> {
  const client = octokit ?? new Octokit({ auth: getEnv("GITHUB_TOKEN") });
  ...
}
```

Not tested: `fetchIssue` error path. The test "throws if GITHUB_TOKEN is not set" covers the env
guard but nothing tests the branch where `octokit.issues.get` itself rejects (404, 401, rate
limit). That failure propagates to `generateSpec` as an undecorated Octokit error, which then
surfaces to the `pipeline.ts` try/catch as `Spec generation failed: HttpError: Not Found` —
accurate but not actionable. A contextual rethrow in `fetchIssue` would improve the operator
experience: `throw new Error(\`Failed to fetch issue #${issueNumber} from ${owner}/${repo}: ${String(err)}\`)`.
